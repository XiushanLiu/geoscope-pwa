## 三条结论

### 一、四轮 verdict 均 `all-ok`，主备顺序无翻转
五路 API 全通 + 九块瓦片拿到字节 + 整轮去重非 fake，三条件每轮都成立。Open-Meteo 四路稳居 157–665 ms，Photon 稳居最慢 930–1265 ms 但仍是唯一可达的反查源。

### 二、真正的性能瓶颈是底图瓦片，不是天气 API
瓦片峰值 **3198 ms**，是 Photon 峰值（1282 ms）的 2.5 倍；瓦片中位 693 ms 也超过了空气、地名、海拔三路。而当前契约是「瓦片 6 s 超时 · **不重试** · 失败转无地图」——**一次慢请求就直接把整张地图打没**，代价远大于任何 API 失败。

3198 ms 已占 6 s 超时的 **53%**，裕度比看上去小得多。

### 三、瓦片内容跨四轮恒定，可以安全缓存
同一 z/x/y 的字节数与指纹在四轮**完全一致**：
- street 42959 / 30226 / 21595 B，fp `f9aa37f8…` / `0ac211a0…` / `e6edb166…`
- imagery 21130 / 21526 / 18642 B，fp `a2cc015f…` / `211adc68…` / `b919edea…`
- dark 10755 / 7594 / 5338 B，fp `9e9ffcc9…` / `a70241df…` / `62bbd26f…`

→ 瓦片内容确定、不随请求变化，**缓存不会拿到脏数据**。

## 据此建议的两处调整

1. **瓦片按 URL 缓存，TTL 7 天**（当前是「不缓存」）。
   ⚠️ 前提：**只在指纹校验判为 real 之后才写缓存**——否则假成功源的占位图会被缓存下来永久中毒。这正是当初选择不缓存的理由，加缓存时必须守住这条。
2. **瓦片失败不要立刻转「无地图」**。改为先降级到「仅网格 + 坐标」，后台静默重试一次，仍然失败才宣布无地图。

## 仍然不变的部分
- API 侧超时 / 重试 / 缓存 TTL / 并发 1 —— 四轮数据全部支持现状，无需调整。
- POI / Overpass：真机未覆盖，按「会失败」设计（8 s 超时、不重试、失败走空态）。
